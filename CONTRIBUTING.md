# Как мы работаем

Проект ведут два фронтенд-разработчика, и работаем мы в разное время. Поэтому всё, что нужно знать второму, — в GitHub: задачи на доске, обсуждения в задачах и PR.

Путь задачи: Backlog → Todo → ветка → Draft PR → Ready for review → ревью → исправления → Approve → Create a merge commit → Done.

## Доска задач

[route-lab-dev / delivery-planner](https://github.com/orgs/route-lab-dev/projects/1)

### Что на доске

Каждая карточка — issue из репозитория. Новый issue попадает на доску сам, в колонку Backlog.

Колонки:

- **Backlog** — задачи на будущее, ещё не запланированы.
- **Todo** — запланированы на текущий спринт, работа не начата.
- **In Progress** — исполнитель работает, ветка создана.
- **In Review** — PR готов к ревью (Ready for review).
- **Done** — PR влит, задача закрыта. Сюда задача переходит сама.

Поля карточки:

- **Type** — Feature, Task или Bug.
- **Size** — S, M или L (см. «Задачи»).
- **Sprint** — двухнедельная итерация: Sprint 1, Sprint 2…
- **Assignees** — исполнитель, всегда один.
- **Linked pull requests** — PR, в описании которого стоит `Closes #N`.

Виды (вкладки над доской):

- **Спринт** — доска только текущего спринта (фильтр `sprint:@current`). Пока спринт не начался, она пустая.
- **Бэклог** — таблица всех задач.

### Как пользоваться

- Клик по карточке открывает справа панель: описание, поля, исполнитель, комментарии.
- Карточку переносят между колонками мышью или меняют поле Status в панели.
- В строке фильтра: `assignee:@me` — только мои задачи; `status:Todo` — одна колонка.

### Жизнь задачи

1. **Завести.** Issues → New issue → шаблон Feature, Task или Bug → заполнить → Create. Задача появится на доске в Backlog.
2. **Запланировать** — на встрече в начале спринта: перенести в Todo, поставить Sprint, Size и Assignees.
3. **Начать.** Перенести карточку в In Progress, создать ветку (см. «Ветки»).
4. **Первый push** → Draft PR с `Closes #N` в описании. PR появится в карточке в поле Linked pull requests.
5. **Ready for review** → перенести карточку в In Review.
6. **Approve → Create a merge commit.** Задача закроется и сама перейдёт в Done.

- Карточку двигает только её исполнитель.
- В Done руками не переносить: задача закрывается через PR.
- Остановился посреди задачи — оставь в ней комментарий: «остановился на …, дальше …».

### Feature и подзадачи

Feature — большая функция, она делится на Task. Открыть Feature → под описанием **Create sub-issue** → тип Task. Прогресс подзадач виден в самой Feature и на доске (поле Sub-issues progress).

## Задачи

- Feature — функция целиком, делится на sub-issues типа Task.
- Task = одна ветка = один PR.
- Size — в часах работы: S — до 3 ч, M — до 8 ч. L — разбить на несколько Task.
- В задаче: цель, проверяемые критерии готовности, что вне рамок.
- Зависимость: Relationships → Mark as blocked by. Общий код (типы, стор, API, моки) — отдельная Task, её вливают первой.
- Параллельные задачи — в разных файлах. Пересечение — договориться до начала.
- Bug — шаги, ожидалось, получилось.

## Работаем в разное время

- Статус работы — на доске, решения — в комментариях задачи или PR, а не только в мессенджере.
- У каждого минимум 2 задачи в Todo: пока PR ждёт ревью, берёшь следующую — ветку от свежего `main`.
- Одновременно у каждого одна задача In Progress.

## Одна задача — два варианта

Иногда одну задачу делают оба, чтобы сравнить подходы. Это двойное время, поэтому — редко.

1. Feature с общими критериями готовности. Контракт (типы, ручки мок-сервера) — отдельной Task, её вливают первой.
2. Две sub-issue типа Task: «… — вариант A» и «… — вариант B», у каждой свой исполнитель и один срок. Ветки `feat/12-call-history-a` и `feat/12-call-history-b`.
3. До Ready for review в чужую ветку не смотреть.
4. Оба PR готовы → каждый ревьюит чужой. В Feature — комментарий «Сравнение»: критерии, понятность, объём, крайние случаи → решение и почему.
5. Вливается один PR. Удачное из второго переносится в него новыми коммитами с трейлером `Co-authored-by: Имя <ID+login@users.noreply.github.com>`. Второй PR закрывается без слияния со ссылкой на решение, его Task — Close as not planned.

## Ветки

- `main` всегда собирается и работает; прямой push запрещён.
- Имя: `тип/номер-кратко` — `feat/12-call-history`, `fix/15-dnd-scroll`.
- Типы: `feat`, `fix`, `refactor`, `test`, `docs`, `style`, `chore`, `ci`.
- Ветка — от свежего `main`, живёт до недели.
- В чужую ветку не пушить.

## Коммиты

- Conventional Commits, на английском, в повелительном наклонении: `feat: add call history card`.
- Каждый коммит ветки попадает в `main`: один коммит — одно логическое изменение, без «fix», «wip», «правки».
- Перед push: `npm run format`, `npm run lint`, `npm run build` — то же, что проверяет CI.
- Новая зависимость — отдельным коммитом: `chore: add vitest`.

## Pull request

- Заголовок — в формате коммита: при слиянии он становится сообщением merge-коммита в `main`.
- Описание — по шаблону, обязательно `Closes #N`: задача закроется при слиянии.
- Draft — сразу после первого push: CI запускается только на PR.
- Ready for review — когда CI зелёный, ветка обновлена с `main`, пройдена самопроверка во вкладке Files changed.
- Размер — до 400 изменённых строк без `package-lock.json`. Больше — делить.
- Только изменения задачи. Попутные правки — отдельным PR.
- После начала ревью — без rebase и force push: исправления новыми коммитами, обновление — Update branch.
- Сливает автор: Approve + зелёный CI + закрытые обсуждения → Create a merge commit.

## Ревью

- Срок — 48 часов с момента запроса. Не успеваешь — напиши в PR, когда посмотришь.
- Ревьюер запускает ветку (`gh pr checkout N`, `npm ci`, `npm run dev`) и проверяет критерии задачи по пунктам.
- Префиксы комментариев: `issue:` — блокирует; `suggestion:` — предложение; `question:` — вопрос; `nit:` — мелочь, не блокирует; `praise:` — что сделано хорошо.
- Правка кода — блоком `suggestion`. Commit suggestion нажимает автор.
- Итог: есть `issue:` — Request changes; нет — Approve.
- Автор отвечает на каждый комментарий: «исправил в `abc1234`» или аргумент.
- Resolve conversation нажимает тот, кто открыл обсуждение.
- После исправлений — Re-request review (⟳ у имени ревьюера).
- Спор дольше двух кругов — созвон, итог — комментарием в PR.

Чек-лист ревьюера:

- [ ] Критерии задачи выполнены — проверено в браузере
- [ ] Нет изменений вне задачи
- [ ] Состояния: пусто, загрузка, ошибка
- [ ] Типы без `any`
- [ ] Имена понятны без комментария
- [ ] Нет отладочного кода: `console.log`, закомментированный код, TODO без задачи

## Готово (Definition of Done)

- Критерии задачи выполнены.
- CI зелёный.
- Approve получен, обсуждения закрыты.
- PR влит через merge commit, задача закрыта через `Closes #N`.
- После настройки деплоя — проверено на GitHub Pages.

## Язык

- Код, имена веток, коммиты, заголовки PR — английский.
- Задачи, описания PR, комментарии в ревью и в коде — русский.

## Спринт — 2 недели

- Одна общая встреча на стыке спринтов, 30–45 минут: демо влитого → ретро (что оставить, что изменить; изменения — задачами) → план: из Backlog в Todo задачи на 2 недели, у каждой Assignees, Size и Sprint.
- Ежедневной отписки нет — статус на доске и в комментариях задач.
- Релиз в конце спринта: Releases → Draft a new release → новый тег `v0.N.0` (N — номер спринта) → Generate release notes → Publish release.

## Команды

```bash
# начать задачу
git switch main
git pull
git switch -c feat/12-call-history

# сохранить работу
git status
git add <файлы>
git commit -m "feat: add call history card"

# первый push; в выводе — ссылка на создание PR
git push -u origin feat/12-call-history

# обновить ветку свежим main
git fetch origin
git merge origin/main

# проверить чужой PR
gh pr checkout 14
npm ci
npm run dev

# после слияния своего PR
git switch main
git pull
git fetch --prune
git branch -d feat/12-call-history

# история main: одна строка = один PR
git log --first-parent --oneline
```

## Типовые ситуации

- **Закоммитил в локальный `main`** → `git switch -c feat/N-name` (коммит переходит в новую ветку) → `git switch main` → `git reset --hard origin/main`. Незакоммиченные изменения перед этим закоммитить.
- **Push в `main` отклонён с `GH013`** → то же: ветка из текущего состояния и PR.
- **Ветку обновили кнопкой Update branch на GitHub** → перед продолжением `git pull`.
- **Конфликт после `git merge origin/main`** → в файлах маркеры `<<<<<<<`, `=======`, `>>>>>>>` → оставить нужный код, удалить маркеры → `git add <файлы>` → `git commit` → `npm run lint`, `npm run build` → `git push`.
- **Конфликт в `package-lock.json`** → руками не править: решить конфликт в `package.json` → `npm install` (npm сам разбирает маркеры в lock-файле) → `git add package.json package-lock.json` → `git commit`.
